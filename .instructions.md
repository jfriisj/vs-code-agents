# Agent Instructions - Persistent Memory (Obsidian Workflow)

All agents interacting with this repository MUST adhere to the following memory and relational graph constraints.

## 1. Zero-Trust Retrieval Gate (MANDATORY)
Before deep-diving into any file or artifact (e.g., `agent-output/planning/`, `agent-output/implementation/`), you MUST first retrieve and read the corresponding `WF-` node in `agent-output/workflows/`.
- **Purpose**: Ensure awareness of context, parent-child relations, and late-breaking status changes.
- **Rule**: If a `WF-` node exists for your task, that node is the entry point for your context retrieval. Do not skip it.

## 2. 10-Line Rule (Memory Constraint)
When creating or updating `WF-` nodes in `agent-output/workflows/`, the "Summary" section MUST NOT exceed 10 lines of actual content.
- **Purpose**: Maintain token efficiency for future retrievals and avoid repeating technical details that exist in implementation artifacts.
- **Automation**: Use `scripts/memory_utils.py` to enforce this rule during node creation.

## 3. Standardized ID Management
All `WF-` nodes, Plans, and Implementation docs MUST use deterministic numbering derived from `agent-output/.next-id`.
- **Rule**: Increment the ID value only when a NEW logical unit (Epic, Plan, Implementer handoff) is created.
- **Access**: Read/Update `agent-output/.next-id` using `scripts/memory_utils.py`.

## 4. Status Idempotency & Handoff Locking
Before updating the `status` of a node (e.g., `Active -> Closed`), you MUST verify that you possess the correct `handoff_id` recorded in the file's frontmatter.
- **Purpose**: Prevent concurrent modification/state corruption between asynchronous agent roles.
- **Rule**: Only use `scripts/memory_utils.py update-status` to change node states.
